# 本地知識迭代系統設計

日期：2026-07-25  
狀態：已由用戶核准設計方向，待書面規格審閱  
工作名稱：Local Knowledge Compiler

## 1. 目標

建立一套不依賴 Obsidian、可由 Codex 與 Claude 共用的本地知識庫。用戶只需把資料放入收件匣，系統便自動保存原始檔、抽取內容、更新 Wiki 與搜尋索引。每次提問時，AI 必須先從本地知識庫建立可追溯的證據包，再用繁體中文交付結論、來源、衝突、信心與未知事項。

系統應具備以下特性：

- 本地優先：知識檔案、索引、紀錄與版本皆存於本機。
- 模型通用：Codex 與 Claude 使用同一套資料和正式規則。
- 持續迭代：新資料或新版本出現後立即排隊處理。
- 精準回答：先檢索證據，再由模型回答；禁止只憑模型記憶作答。
- 可追溯：重要結論可追到原始檔及頁碼、段落、儲存格或時間戳。
- 可復原：原始資料不可覆寫，所有知識修改皆有 Git 版本。
- 可擴充：先支援數百份資料，日後可擴展至數萬份而不搬遷內容。

## 2. 已確認的使用需求

- 入口：用戶直接在 Codex 或 Claude 對話中提問。
- 資料種類：文字、網頁存檔、PDF、Word、Excel、對話結論、專案文件、程式碼、圖片、截圖、影片與錄音。
- 範圍：一座總知識庫，內部分成個人、工作、各專案與共享區。
- 自動權限：AI 可全自動分類、合併、改寫與淘汰 Wiki；原始資料不可永久刪除。
- 更新時機：新資料放入後立即排隊整理。
- 回答格式：直接結論、資料重點、來源、衝突、時效、信心、未知事項與自動回寫。
- 規模：可由小型逐步擴展至大型。
- 語言：來源不限語言，交付統一使用繁體中文。
- 網路邊界：回答只使用本地知識庫，不主動搜尋網路。
- 並行：Codex 與 Claude 可能同時讀寫。

## 3. 核心原則

### 3.1 三層知識

1. **原始來源層**：用戶提供的原始檔及其歷史版本。不可改寫，是最終證據。
2. **Wiki 層**：AI 維護的概念、人物、工具、主題、決策與專案頁。
3. **規則層**：定義收錄、更新、引用、查詢、回寫與健康檢查方式。

這延續 Karpathy 的 LLM Wiki 思路，但增加事件佇列、並行控制、來源定位、驗證與復原機制。

### 3.2 檔案是主體，資料庫只是索引

Markdown 與原始檔是長期真相。SQLite 僅用於全文搜尋、別名、關係和工作狀態。索引損壞時，必須能從檔案完整重建。

### 3.3 禁止知識自我污染

- 原始來源的證據權重高於 Wiki。
- Wiki 的證據權重高於衍生問答。
- 衍生問答不得引用自己來提高事實信心。
- 沒有原始來源支持的新推測，只能標為推論或未知。
- 新舊來源矛盾時並列呈現，不得偷偷選擇其中一方。

## 4. 本地資料夾架構

```text
KnowledgeBase/
├── 00_inbox/                         # 用戶投放新資料
├── 10_raw/                           # 不可修改的原始證據
│   ├── personal/
│   ├── work/
│   ├── projects/<project_slug>/
│   ├── shared/
│   └── unclassified/                  # 空間不確定時的安全隔離區
├── 20_wiki/                          # AI 維護的知識
│   ├── personal/
│   ├── work/
│   ├── projects/<project_slug>/
│   ├── shared/
│   └── unclassified/
│       ├── concepts/
│       ├── entities/
│       ├── topics/
│       ├── decisions/
│       └── timelines/
├── 30_answers/                       # 值得保留的問答成果
├── 40_index/
│   ├── index.md                      # 人與 AI 可讀的總目錄
│   ├── catalog.sqlite                # 可重建的搜尋索引
│   └── cache/                        # 可重建的抽取文字與快取
├── 80_system/
│   ├── KNOWLEDGE_PROTOCOL.md         # 唯一正式作業規則
│   ├── config.toml
│   ├── schemas/
│   └── prompts/
├── 90_logs/
│   ├── events.jsonl                  # 只追加事件紀錄
│   ├── ingestion/
│   └── queries/
├── 99_trash/                         # 可復原回收區
├── AGENTS.md                         # Codex 薄入口
├── CLAUDE.md                         # Claude 薄入口
└── .kb/                              # 佇列、鎖、暫存；不進 Git
```

`AGENTS.md` 與 `CLAUDE.md` 不複製整套規則，只要求對應 AI 讀取並遵守 `80_system/KNOWLEDGE_PROTOCOL.md`。正式規則只有一份，避免兩邊逐漸分歧。

## 5. 來源與 Wiki 資料模型

### 5.1 原始來源

每次收錄產生不可變的 `source_id` 與 `version_id`。來源目錄保存：

- 原始檔。
- 內容雜湊。
- 原始檔名、類型、大小與收錄時間。
- 所屬空間：personal、work、project、shared 或 unclassified。
- 上一版本與取代關係。
- 抽取狀態與錯誤狀態。

同名檔案內容改變時，不覆蓋舊檔；建立新版本並記錄差異。完全相同的內容以雜湊去重，只建立關聯，不重複編譯。

系統可自動判斷空間，但不得把低信心結果放入 `shared`。無法可靠判定個人、工作或專案歸屬時，先放入 `unclassified`；此區預設不參與一般跨區查詢，避免私人內容意外混入工作回答。

### 5.2 Wiki 頁

每篇 Wiki 頁至少包含：

```yaml
id: 穩定識別碼
title: 顯示名稱
aliases: []
type: concept | entity | topic | decision | timeline | project
space: personal | work | shared | unclassified | project:<slug>
status: active | disputed | stale | archived
confidence: high | medium | low
updated_at: ISO-8601 時間
source_ids: []
```

正文固定分成：

- `Current State`：目前最新、最可信的整理結果，可被新證據更新。
- `Evidence`：結論與來源定位。
- `Conflicts and Gaps`：矛盾、缺口與尚待確認事項。
- `Related`：相關 Wiki 頁與原始來源。
- `Timeline`：只追加的知識演變紀錄。

### 5.3 來源定位

引用定位依檔案種類保存：

- 文字／Markdown／程式碼：標題與行號。
- PDF：頁碼與抽取段落。
- Word：章節或段落。
- Excel：工作表與儲存格範圍。
- 圖片：OCR 區塊或圖像說明。
- 音訊／影片：開始與結束時間戳。

## 6. 即時收錄與編譯流程

### 6.1 工作狀態

```text
discovered
→ stable
→ fingerprinted
→ archived
→ extracted
→ compiled
→ validated
→ published
```

失敗狀態為 `retrying` 或 `pending_attention`。失敗工作不得發布半成品。

### 6.2 流程

1. 守門員監看 `00_inbox/`。
2. 等待檔案大小和修改時間穩定，避免讀到仍在複製的檔案。
3. 計算雜湊，判斷新來源、重複來源或既有來源的新版本。
4. 將原始檔歸檔到 `10_raw/`，從此禁止原地修改。
5. 依類型抽取可搜尋文字，結果放入可重建快取。
6. 建立編譯工作，送入單一寫入佇列。
7. 可設定 Codex 或 Claude 為背景編譯器；編譯器不可用時保留工作，待恢復後續跑。
8. AI 只更新受影響的 Wiki 頁、索引與時間線。
9. 驗證格式、引用、連結、來源存在性與空間權限。
10. 在暫存區完成整批變更後，以原子方式發布。
11. 寫入事件紀錄並建立 Git 版本。

### 6.3 媒體抽取

- 第一層：Markdown、文字、JSON、CSV、程式碼直接處理。
- 文件層：PDF、DOCX、XLSX、PPTX 使用獨立抽取器。
- 視覺層：圖片與掃描 PDF 使用 OCR，並降低低品質辨識結果的信心。
- 影音層：音訊與影片先轉錄，再以時間戳引用。

若缺少抽取能力，原檔仍正常歸檔，狀態標為 `pending_extractor`；系統不得假裝已讀取內容。目前環境已有 Python 3.13、Node.js 與 Git，但沒有 Pandoc 與 FFmpeg，因此影音與部分文件處理需在實作計畫中安排可攜式抽取器或明確降級路徑。

由於回答被限定為只使用本地資料，裸網址不會被系統自動連線下載。網頁內容必須先另存為 HTML、Markdown、PDF 或其他本地檔案；只有網址的檔案可作為書籤登記，但在內容尚未保存前不能成為回答證據。

## 7. 精準查詢流程

Codex 與 Claude 都必須先執行同一個本地查詢命令：

```text
kb prepare "<question>"
```

### 7.1 查詢階段

1. **問題拆解**：辨識實體、主題、專案、時間範圍、任務類型與所需輸出。
2. **空間判定**：預設只搜尋問題相關空間；跨個人與工作資料需要問題本身明確要求。
3. **新鮮度閘門**：檢查相關的新資料是否仍在處理。可短暫等待；超時則在回答標示尚未完成的工作。
4. **多路召回**：
   - 標題與穩定 ID 精確搜尋。
   - SQLite FTS5 全文搜尋。
   - 中文、英文、縮寫與舊名稱的別名展開。
   - Wiki 雙向連結、共同來源與相關決策擴展。
   - 時間與版本條件。
5. **排序與去重**：
   - 問題相關性。
   - 原始來源優先。
   - 來源新鮮度，但不得無條件以最新取代較可靠來源。
   - 來源信心與抽取品質。
   - 直接證據優先於衍生摘要。
6. **建立證據包**：
   - 最相關 Wiki 的 Current State。
   - 支持結論的原始片段。
   - 反方、衝突或較新片段。
   - 決策與演變時間線。
   - 每段的本地來源定位。
   - 尚在處理或讀取失敗的相關資料。

### 7.2 回答階段

AI 只能根據證據包回答，固定使用繁體中文並包含：

1. 直接結論。
2. 相關資料重點。
3. 每項重要結論的來源與定位。
4. 新舊資料衝突與過期提醒。
5. 信心程度及理由。
6. 本地資料無法確定的部分。
7. 建議的下一個本地資料缺口；不得自行上網補充。

完成後執行：

```text
kb finalize
```

它保存問答報告、記錄本次使用的來源，並把有來源支持的新洞見送入寫入佇列。回寫仍須通過相同的引用與格式驗證。

## 8. 並行與一致性

- 查詢工作可並行讀取已發布快照。
- 所有 Wiki、索引和紀錄修改必須進入單一寫入佇列。
- writer 取得 `write.lock` 後，才可建立暫存變更。
- 發布前重新確認基礎版本；若已被其他工作更新，重新套用或重跑。
- 多檔案修改視為同一批交易：全部驗證通過才發布。
- Codex 與 Claude 不直接繞過佇列修改受管理資料。

## 9. 錯誤處理與復原

- 每個工作最多自動重試三次；之後進入 `pending_attention`。
- 抽取失敗、格式損壞或不支援類型不阻止原始檔歸檔。
- 程序中斷後依事件紀錄續跑，已完成步驟不重複執行。
- 暫存區不得被查詢看見。
- 永久刪除不開放給 AI；淘汰頁面移入 `99_trash/`。
- SQLite 索引可由原始檔與 Markdown 全量重建。
- Git 保存每批知識修改；還原後索引隨檔案狀態重建。

## 10. 健康檢查

即時編譯只檢查受影響頁面。系統空閒時定期執行全庫健康檢查：

- 失效連結與孤兒頁。
- 重複概念與別名碰撞。
- 缺少來源的結論。
- 被新版本取代但仍標為有效的說法。
- 不同頁面間的矛盾。
- 有重要提及但沒有獨立頁面的概念。
- 長期失敗或尚待抽取的來源。
- 索引與檔案內容不一致。

健康檢查只產生可驗證的修復工作，不直接永久刪除資料。

## 11. 第一版驗收標準

1. 放入新檔案後，自動歸檔、抽取、建立 Wiki 更新與來源引用。
2. 完全相同的檔案不重複編譯；內容更新後保存新舊版本及差異。
3. Codex 與 Claude 可使用同一套 `prepare`、回答和 `finalize` 流程。
4. 兩個 AI 同時提交修改時，不得覆蓋或破壞資料。
5. 處理途中強制中斷，重啟後能續跑且不發布半成品。
6. 刪除 `catalog.sqlite` 後，可從檔案重建等價索引。
7. 本地沒有證據的問題必須明確回答無法確定。
8. 每項重要結論能追到原始來源定位。
9. 修改錯誤時能從 Git 還原，原始資料未受影響。
10. 查詢個人、工作或專案時，預設不混入無關空間。

## 12. 第一版範圍與延後項目

第一版包含：

- 資料夾骨架與正式規則。
- 收件匣監看、雜湊、去重、版本與工作佇列。
- 常用文字及文件抽取接口。
- Markdown Wiki、SQLite FTS5 與 `index.md`。
- Codex／Claude 共用的 prepare/finalize 查詢協定。
- 單一 writer、驗證、事件紀錄、Git 版本與回收區。
- 最小健康檢查與索引重建。

第一版不包含：

- 圖形化桌面 App 或網頁聊天介面。
- Obsidian。
- 自動網路搜尋。
- 向量資料庫、知識圖資料庫或本地大型模型。
- 多人權限與遠端同步。
- 永久自動刪除。

當全文搜尋和關係擴展不足以支撐實際規模時，再新增向量或混合搜尋；它只能替換搜尋模組，不改變 Markdown 與原始檔架構。

## 13. 成功定義

用戶能將任意資料放入 `00_inbox/`；系統會安全歸檔所有檔案，並處理已有抽取器支援的內容。暫不支援或抽取失敗的資料會明確標為等待處理，不會被誤稱為已讀取。之後用戶可在 Codex 或 Claude 直接用自然語言提問，系統會以最新已完成的本地知識建立證據包，交付繁體中文、附來源、顯示衝突和信心的回答；有價值的新分析會安全回寫，讓後續問題建立在累積成果上。模型可以更換，知識檔案、引用、規則與歷史不需要搬遷。
