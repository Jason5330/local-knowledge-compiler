# 本地知識庫完整運作原理（零技術版）

這份文件不假設你會寫程式。它要回答的不是只有「按哪裡」，還包括：

- Excel 放進去後，系統實際做了什麼？
- 為什麼不能直接改原始資料？
- Wiki 是什麼？在哪一層更新？
- index 是何時建立的？為什麼需要它？
- 提問時怎麼找資料？為什麼要這樣找？
- 回答會不會自動保存？保存在哪裡？
- 回答錯了，系統怎麼記住並避免再犯？

## 先用一句話理解

這套系統把資料分成三種：

```text
原始證據：Excel 原檔的安全副本，不能被 AI 改寫
整理知識：AI 根據證據製作的 Wiki 筆記，可以重新整理
使用記憶：保存過的回答與錯誤修正，幫助下一次回答
```

最重要的規則是：

```text
原始 Excel 證據 ＞ 修正紀錄 ＞ AI 自己的猜測
```

如果整理筆記、舊回答或 AI 的印象和原始 Excel 衝突，必須以原始證據為準。

---

## 一、什麼是「證據」？

這裡的「證據」不是法律文件，也不是 AI 說「我認為是這樣」。它是從原始資料取出的
一段真實內容，而且必須帶著能回去核對的位置與版本。

例如：

```text
證據內容：A 產品五月營收 320
原始檔案：2026年銷售表.xlsx
檔案版本：ver_abc123……
工作表：五月銷售
位置：B12～D12
欄位單位：萬元
```

所以一份合格證據不是只有「320」這個數字，而是：

```text
內容＋來源位置＋來源版本
```

只有內容而沒有來源位置，人就找不到它；只有檔名而沒有工作表和位置，複雜 Excel 仍然很難核對；
沒有來源版本，則無法知道 AI 看的是上個月舊檔還是這個月新檔。

### 為什麼要有證據？

AI 很擅長閱讀與整理文字，但它仍可能：

- 把「萬元」看成「元」。
- 把兩張工作表的數字混在一起。
- 使用舊版 Excel 的資料回答新版問題。
- 在資料不足時補出一個聽起來合理、實際不存在的答案。

有證據後，系統才能做到：

```text
AI 說出結論
→ 同時指出原始檔、版本、工作表和位置
→ 人可以回到 Excel 核對
→ 保存前，電腦也能檢查引用是否真的存在
```

證據的目的不是保證 AI 永遠不會錯，而是讓錯誤「可以被發現、可以被追查、可以被修正」。

### 證據何時出現？

證據會在整個流程中出現多次，但每次作用不同：

1. **資料匯入時**：系統讀取 Excel，建立可定位的小片段，記住工作表、範圍、版本與內容指紋。
2. **使用者提問時**：`40_index` 從大量片段中挑出最相關的原始證據，放進這次問題的證據包。
3. **AI 回答時**：AI 用證據作答，並把來源位置當成引用一起交給你。
4. **保存回答時**：系統再次確認引用的證據仍存在、版本和內容指紋沒有改變，才准寫入 `30_answers`。
5. **回答回錯時**：系統重新查看原始證據，只有找到明確錯因，才可寫入 `50_corrections`。
6. **Wiki 更新時**：整理後的結論要保留它依據哪些原始證據；沒有來源關係的內容不能冒充可靠事實。

需要特別區分：

```text
原始 Excel 的可定位內容 ＝ 原始證據
Wiki                         ＝ 根據證據整理的筆記
已保存回答                   ＝ 根據證據留下的結論紀錄
修正紀錄                     ＝ 根據證據建立的防錯提醒
AI 自己的說法                ＝ 不是證據
```

## 二、完整資料夾地圖

初始化後，專案裡會建立一個只留在本機的 `KnowledgeBase/`：

```text
KnowledgeBase/
├── 00_inbox/          新資料的入口
├── 10_raw/            不可任意改動的原始證據副本
├── 20_wiki/           AI 整理後的知識筆記
├── 30_answers/        你明確同意保存的回答
├── 40_index/          電腦使用的本機搜尋索引
├── 50_corrections/    回答錯誤的修正記憶
│   ├── records/       每一條修正目前的完整內容
│   └── timeline/      每一條修正的歷史變化
├── 80_system/         知識庫規則、設定與版本資料
├── 90_logs/           執行紀錄
├── 99_trash/          已處理的 inbox 副本與可回查暫存
└── .kb/               系統工作區：佇列、暫存、鎖定檔
```

`.kb` 的名稱以一個點開頭，所以檔案總管有時不會顯示。它不是遺失，也不是知識內容；
它像餐廳廚房的「出單區」，記錄哪個工作排隊、處理到哪裡，避免同一份資料同時被處理兩次。

### 每一層負責什麼

| 位置 | 白話用途 | 為什麼需要 |
|---|---|---|
| `00_inbox` | 你放入新資料「副本」的入口 | 把待處理資料和已保存證據分開，避免混亂 |
| `10_raw` | 保存內容完全一致的來源版本 | 日後可核對、重建、追查，不讓 AI 改掉證據 |
| `20_wiki` | AI 整理出的主題筆記 | 不必每次從幾萬列 Excel 重新理解整個背景 |
| `30_answers` | 你要求保存、而且通過檢查的回答 | 留下已採用的結論、引用與當時依據 |
| `40_index` | 給電腦快速搜尋的目錄 | 不必每問一次就重新打開所有 Excel |
| `50_corrections` | 有證據的錯誤修正與歷史 | 相似問題出現時，先提醒 AI 不要重犯 |
| `80_system` | 系統規則和設定 | 讓 Codex、Claude Code 都遵守同一套規則 |
| `90_logs` | 處理過程紀錄 | 發生問題時能查到在哪一步失敗 |
| `99_trash` | 已處理的入口副本等可回查資料 | inbox 保持乾淨，同時保留追查機會 |
| `.kb` | 工作佇列、暫存區與防撞鎖 | 中斷後可繼續，並避免兩個 AI 同時寫壞資料 |

## 三、初始化時發生什麼事

當你說「初始化本專案知識庫」時，系統會：

```text
建立 KnowledgeBase 標準資料夾
→ 寫入共同使用規則
→ 建立空的搜尋資料庫 40_index/catalog.sqlite3
→ 設定 Git 防誤上傳
→ 執行 status 與 lint 健康檢查
```

### 何時建立 index？

第一個主要 index（搜尋索引）在初始化時就建立，但一開始是空的：

```text
KnowledgeBase/40_index/catalog.sqlite3
```

每次有新 Excel 成功讀取後，系統才把它的「可搜尋文字、位置和來源身分」加入 index。

修正用的 index 則在第一條修正建立或更新時產生。它和原始資料索引分開，因為兩者用途不同：

- 原始資料 index：回答「資料在哪裡、內容是什麼」。
- 修正 index：回答「這次問題是否像以前犯過的錯」。

### 為什麼要有 index？

把 index 想成書本最後面的索引頁：

```text
沒有 index
→ 每問一次都要重新翻完所有 Excel
→ 慢、容易漏掉，也浪費 AI 可讀取的內容額度

有 index
→ 先找到最可能相關的工作表、欄位、儲存格範圍
→ 再把少量精準證據交給 AI
```

index 只是「地圖」，不是原始證據。它壞掉或刪失時，可以用 `10_raw` 重新建立；不能反過來
把 index 當成唯一資料來源。

## 四、原始 Excel 進去後如何整理

假設你有一份 `2026年銷售表.xlsx`。

### 第 1 步：只放副本進 `00_inbox`

```text
你原本保存的 Excel
→ 保持原位、不移動、不修改
→ 複製一份到 KnowledgeBase/00_inbox/
```

為什麼不能直接改原始資料？

因為處理工作可能搬動入口檔案，而且 AI 或程式也可能判讀錯誤。保留原本唯一檔案，可以確保
任何時候都有一份不受系統影響的底稿。

### 第 2 步：建立處理工作

系統替這份副本建立一個工作編號，先放進 `.kb/queue`，處理時再移到 `.kb/staging`。

為什麼這樣做？

- 電腦或 AI 中途關閉時，知道工作停在哪裡。
- 避免同一份 Excel 被重複處理。
- 兩個程序同時操作時，用鎖定檔避免彼此覆蓋。

### 第 3 步：替內容計算「數位指紋」

系統會計算 SHA-256。你不必理解數學，只要把它想成「依檔案內容產生的超長指紋」：

```text
完全相同的內容 → 指紋相同 → 不重複保存
內容只改一個字 → 指紋不同 → 視為新版本
```

這能判斷同一檔案是否已處理，也能在日後證明引用的證據沒有偷偷改變。

### 第 4 步：保存不可任意改動的版本

檔案副本和來源說明會放到：

```text
10_raw/<資料空間>/<來源編號>/<版本編號>/
├── 2026年銷售表.xlsx
└── manifest.json
```

`manifest.json` 像檔案的身分證，記錄名稱、版本、指紋、時間等資訊。

為什麼要保存版本，而不是只留下最新一份？

- 新版數字有問題時，可以回看舊版。
- 能回答「當時的資料為什麼得出這個答案」。
- index 損壞時，可從原始版本重新建立。
- AI 整理錯了，也不會破壞真正證據。

### 第 5 步：把複雜檔案拆成可定位的小片段

系統讀取 Excel 時，不會只留下模糊的「我看過這個檔案」，而會記住：

```text
檔案名稱
→ 工作表名稱
→ 儲存格或資料範圍
→ 欄位與文字內容
→ 對應的來源版本
```

這些片段不是把 Excel 隨便切碎，而是讓回答可以指出「證據在銷售表的哪一張工作表、哪個範圍」。
對 PDF 會盡量記頁碼，對文字檔會記行或段落；不同格式使用適合自己的定位方式。

如果遇到掃描圖片、特殊格式或目前不支援的內容，系統會標記 `pending_extractor`：

```text
原始檔仍安全保存
→ 但系統承認目前讀不到內容
→ 不准 AI 假裝已經讀完
```

### 第 6 步：更新 `40_index`

成功讀出的片段會寫入 `40_index/catalog.sqlite3`。相同版本若重新處理，系統會更新該版本的
索引項目，而不是不斷堆出重複資料。

這一層主要保存：

- 來源和版本身分。
- 可搜尋的小片段。
- 每個片段在原檔的位置。
- 用來快速全文搜尋的資料。

### 第 7 步：檢查舊修正是否仍適用

如果這份 Excel 是某個舊資料來源的新版本，系統會檢查 `50_corrections` 裡相關的修正。
例如舊表的金額單位是「萬元」，新表改成「元」，舊規則就不能盲目套用。

### 第 8 步：整理 Wiki

系統可根據原始證據製作或更新 `20_wiki` 裡的主題筆記。這一步是「整理層」，不是改 Excel。
若 AI 整理服務暫時不能工作，原始資料和 index 仍會保留，並標記 `pending_attention` 等待繼續。

### 第 9 步：清理入口

成功處理後，`00_inbox` 的那一份入口副本會移到 `99_trash/processed-inbox/...`。

為什麼不一直留在 inbox？

因為 inbox 代表「還沒處理」。處理完仍放著，下一次會讓人誤以為還有新資料；而移到可回查區，
又比立即刪除更安全。

完整流程是：

```text
原檔保持不動
→ 副本放入 00_inbox
→ .kb 排隊與暫存
→ 10_raw 保存原始版本
→ 讀成可定位片段
→ 40_index 建立搜尋地圖
→ 重驗 50_corrections
→ 視情況更新 20_wiki
→ 入口副本移到 99_trash
```

## 五、什麼叫 Wiki？Wiki 更新在哪一層？

這裡的 Wiki：

- 不是維基百科。
- 不是公開網站。
- 不需要安裝 Obsidian。
- 就是一組放在本機的 Markdown 文字筆記。

Wiki 更新只發生在：

```text
KnowledgeBase/20_wiki/
```

最簡單的比喻：

```text
10_raw 原始 Excel ＝ 會計帳本、原始證據
20_wiki            ＝ 根據帳本整理的重點筆記
30_answers         ＝ 你確認要留下的某次完整問答
```

例如 Excel 有 20 張表和數萬列，Wiki 可以整理成：

- 某客戶目前的基本狀態。
- 某產品最新規格。
- 每月銷售重點。
- 幾份資料之間的關係。
- 每個整理結論來自哪個原始來源。

### 為什麼要建立 Wiki？

index 擅長「找出含有某些字的精確片段」，但不擅長用人類容易閱讀的方式講完整背景。
Wiki 則負責把零散證據整理成主題，讓下一次提問更快理解上下文。

### Wiki 何時更新？

常見時機有兩種：

1. 新原始資料成功進入知識庫後，系統整理相關主題。
2. 你明確保存一個有引用、通過檢查的回答後，系統把值得保留的結論整理進相關主題。

### Wiki 可以相信到什麼程度？

Wiki 是「衍生資料」，可以重新整理，也可能過時。回答金額、日期、規格等事實時，系統仍要回頭
核對 `10_raw` 的原始證據。Wiki 可以幫助理解，不能取代原始 Excel。

每一篇 Wiki 應保留來源身分或引用關係。找不到原始來源的 Wiki 內容，不應被當作可靠證據。

## 六、提問時怎麼找資料

當你說「用我的知識庫回答這個問題」時，不是讓 AI 隨意翻資料。系統先執行 `prepare`，
製作一包只屬於這個問題的「證據包」。

### 第 1 步：確認問題與資料空間

如果你把資料分成個人、工作、共用或不同專案，系統先限制搜尋範圍。

為什麼？

避免把 A 客戶的資料和 B 客戶混在一起，也避免個人資料誤進工作答案。

### 第 2 步：搜尋原始資料 index

系統會使用：

- 問題中的完整文字。
- 重要關鍵字和可能的替代說法。
- 精確編號、檔名、工作表名或位置。
- 搜尋結果與問題的符合程度。

原始證據永遠優先，而且排在證據包前面。

### 第 3 步：補充少量 Wiki 背景

系統可能加入少量 `20_wiki` 的整理內容，幫助 AI 理解主題關係。但必須：

- 清楚標示它是整理內容，不是原始資料。
- 能追溯到原始來源。
- 數量有限，不能讓 Wiki 淹沒真正證據。

### 第 4 步：自動搜尋相似修正

系統另外搜尋 `50_corrections`，比較：

- 是否同一資料空間。
- 是否相同檔案類型或來源家族。
- 工作表、欄位、單位是否相似。
- 問題類型和關鍵字是否相似。

相似度強或中等的修正會要求 AI 明確處理；較弱的只作「可能相關」提醒。這種比對採用可以解釋的
欄位，不只憑 AI 感覺說「好像很像」。

### 第 5 步：建立問題專屬證據包

證據包包含：

- 原始問題。
- 搜尋空間。
- 相關證據片段。
- 精確來源、版本、工作表與位置。
- 證據內容指紋。
- 適用或可能適用的修正。
- 尚未完成工作的警告。
- 回答與引用規則。

為什麼要先做證據包？

```text
搜尋階段先固定「這次可以使用哪些證據」
→ AI 根據這包資料回答
→ 保存前再用同一包資料機械檢查引用
```

這樣能減少 AI 引用不存在的工作表、把舊版本說成新版本，或回答後才偷偷換證據。

搜尋有數量上限。如果資料多到結果被截斷、索引損壞或證據不足，系統應警告，必要時禁止保存，
而不是把不完整結果冒充完整答案。

### 第 6 步：AI 作答

AI 必須：

1. 先讀原始證據。
2. 使用 Wiki 了解背景，但不讓它取代原始證據。
3. 檢查適用的錯誤修正。
4. 清楚標示引用位置。
5. 證據不足就說無法確定。

提問時怎麼找資料的完整流程：

```text
你的問題
→ 限定資料空間
→ 40_index 找原始證據
→ 少量 20_wiki 補背景
→ 50_corrections 找相似錯誤
→ 組成問題專屬證據包
→ AI 根據證據回答並引用
```

## 七、回答會不會自動保存？

不會。

你在 Codex 或 Claude Code 看到的一般回答，只存在當下對話。系統不會因為同樣的問題問過一次，
就偷偷把回答寫回知識庫。

只有你明確說：

```text
保存這次回答
```

系統才會執行保存檢查。這個設計避免把試問、誤答、半成品和敏感對話全部永久留下。

### 保存前檢查什麼？

系統會確認：

- 引用確實存在於這次證據包。
- 引用內容和指紋沒有改變。
- 每一條適用修正都有「已套用」或「不適用」的說明。
- 沒有尚未解決的修正衝突。
- 搜尋沒有因截斷或損壞而不完整。
- 信心和引用格式符合規則。

檢查不通過，就不保存。這比讓 AI 自己說「我檢查過了」更可靠。

### 回答保存在哪裡？

成功保存後會寫成 Markdown 文字檔：

```text
KnowledgeBase/30_answers/<年份>/<日期>-<隨機編號>.md
```

內容會包括問題、結論、引用、衝突、信心與修正處理紀錄。

### 為什麼要保存回答？

- 留下你當時採用的結論。
- 記錄答案使用了哪些來源版本。
- 日後發現問題時可以追查。
- 讓有證據的成熟結論參與 Wiki 整理。

保存的回答仍然不是原始證據，也不會被塞回 `10_raw` 或冒充 Excel 內容。

### 保存後 Wiki 怎麼更新？

保存成功後，系統建立一個「衍生整理工作」：

```text
30_answers 已保存回答
→ 核對其中引用
→ 把值得保留的結論整理進 20_wiki
→ 保留來源關係
```

如果 Wiki 整理工作無法完成，已保存答案仍在；系統會留下待處理狀態，不會假裝 Wiki 已更新。

## 八、回答錯了：完整回錯機制

當你發現答案錯誤，直接說：

```text
這個回答錯了
```

這不是單純要求 AI 「再猜一次」，而是啟動錯誤回饋流程。

### 第 1 步：取回剛才的問題與證據包

系統先確認剛才到底用了哪份 Excel、哪個版本、哪張工作表和哪個範圍。

### 第 2 步：重新核對原始證據

AI 必須回到 `10_raw` 對應證據，而不是只看自己上一段回答或 Wiki。

例如：

```text
錯誤答案：營收是 320 元
原始欄位：數值 320，表頭單位為「萬元」
正確解讀：320 萬元
```

### 第 3 步：只有具體證據才建立修正

允許建立修正的情況：

- 你明確回報這個回答錯了，而且重新核對到原因。
- 電腦能確定引用身分錯誤、小數位關係錯誤或單位換算錯誤。

不能建立修正的情況：

- AI 只是主觀懷疑。
- 找不到原始證據。
- 只根據 Wiki、舊回答或想像中的規則。

### 第 4 步：保存修正目前內容與歷史

```text
50_corrections/
├── records/<修正編號>.json
└── timeline/<修正編號>.jsonl
```

`records` 保存這條修正目前有效的完整狀態；`timeline` 只追加歷史事件，例如建立、再次發生、
改成暫停或退役。

為什麼兩份都要？

- `records`：下次搜尋時快速讀取目前規則。
- `timeline`：保留「何時、為什麼改變」，避免歷史被覆蓋後無法追查。

相同錯誤再次出現時，系統會辨認為同一修正並追加發生紀錄，不會無限建立重複規則。

### 第 5 步：建立或更新修正 index

修正建立後，搜尋資料寫入 `40_index` 下的修正索引。未來提問時，不必讀完所有修正檔案，
就能先找到同類型、同工作表、同欄位或同單位的錯誤。

### 第 6 步：未來相似問題自動提醒

下次 prepare 時，系統會先讀這份修正紀錄。AI 必須對每一條強相關修正說明：

- `applied`：這次有套用。
- `not_applicable`：這次不適用，並說明原因。
- `conflict`：修正和目前證據衝突。

若有未解決的 `conflict`，系統禁止保存答案。

完整回錯閉環：

```text
你說「這個回答錯了」
→ 回到原始 Excel 重新核對
→ 找到明確錯因
→ 寫入 50_corrections 的目前規則與歷史
→ 更新修正 index
→ 下次相似問題 prepare 自動帶入
→ AI 必須交代是否套用
→ finalize 再檢查才准保存
```

## 九、新 Excel 進來後，舊修正怎麼辦？

資料會持續更新，所以修正不能永久盲目套用。新版本進入 index 後，系統會重新驗證同一資料空間、
同一來源家族的相關修正。

| 狀態 | 白話意思 | 回答時如何處理 |
|---|---|---|
| `active` | 表格結構仍符合，修正有效 | 相似問題會自動提醒 |
| `stale` | 工作表、欄位或單位可能已改版 | 不盲目套用，等待確認 |
| `suspended` | 發現明確例外，或你要求暫停 | 暫時不自動套用 |
| `retired` | 這條規則永久退役 | 只保留歷史，不會自動恢復 |

如果重驗工作失敗，新的原始 Excel 和 index 不會因此被刪掉；系統會標記
`correction_revalidation.pending_attention`，提醒 AI 或使用者稍後處理。

## 十、系統出錯或中斷時怎麼保護資料

### `pending_attention`

意思是「有一步需要 AI 接手」，不代表資料消失。工作編號和進度仍保存在 `.kb`。

### `pending_extractor`

意思是「檔案已保存，但目前的讀取器無法可靠理解內容」。系統必須承認讀不到，不能生成假答案。

### `status`

用來看目前排隊、處理中、待接手的工作，以及修正的 `active`、`stale`、`suspended`、
`retired` 數量。

### `lint`

這是只讀健康檢查，會核對原始版本、索引、Wiki 來源關係、修正記錄、時間線和生命週期是否一致。
它主要負責「找問題」，不會隨便重寫你的資料。

### `rebuild`

如果 index 損壞，可使用 rebuild：

```text
重新讀取 10_raw 的已驗證原始版本
→ 建立新的原始資料 index
→ 從 50_corrections 正式記錄重建修正 index
→ 成功後才替換舊 index
```

為什麼 rebuild 安全？

因為 index 是可重建地圖，真正來源仍是 `10_raw` 和 `50_corrections` 的正式記錄。rebuild
不應改寫原始 Excel，也不是遇到任何問題都先亂按的萬用修復鍵；應先看 status 和 lint。

## 十一、GitHub、隱私與 OneDrive

```text
公開 GitHub Repo
＝程式、空白架構、教學文件

本機 KnowledgeBase
＝你的 Excel、索引、Wiki、回答、修正
```

Repo 已用 Git 忽略規則、提交前檢查和推送前檢查保護 `/KnowledgeBase/`。正常操作下，
KnowledgeBase 和你的資料不會上傳 GitHub。

但仍要注意：

- 不要手動把私人資料貼進 README、Issue、PR 或提交訊息。
- 不要要求 AI 把真實的 `KnowledgeBase` 內容加入公開範例。
- Codex 或 Claude Code 可能使用雲端模型；「檔案存在本機」不等於傳給模型的片段永遠離線。
- 公司機密、個資仍必須遵守公司的 AI 與資料政策。

放在 OneDrive 可以使用，但避免兩台電腦同時寫入同一個知識庫。OneDrive 同步衝突可能複製檔案，
而 `.kb` 的鎖定主要防同一台電腦上的同時寫入，不能保證跨電腦同步完全不衝突。

## 十二、用一個完整例子串起來

你把 `2026年銷售表.xlsx` 的副本放進 inbox：

```text
→ 20_wiki 整理銷售主題背景
```

你問：「五月 A 產品營收是多少？」

```text
40_index 找到五月、A 產品與營收欄位
→ 補充少量 Wiki 背景
→ 檢查是否有單位相關修正
```

你沒有說保存：

```text
答案只留在這次對話

```

你說「保存這次回答」：

```text
檢查引用和修正
→ 30_answers 保存答案
→ 建立 Wiki 整理工作
→ 20_wiki 更新相關主題
```

如果答案把「萬元」看成「元」，你說「這個回答錯了」：

## 十三、這套架構的優點與限制

### 優點

- 原始資料、整理內容、回答記憶分層，不容易互相污染。
- 每個答案可帶精確來源，方便核對。
- index 可重建，損壞不等於原始資料消失。
- 回答不會未經同意全部永久保存。
- 錯誤修正能在相似問題中自動出現。
- Markdown、Excel 和本機資料夾是通用格式，可同時給 Codex、Claude Code 使用。

### 限制

- AI 仍可能理解錯誤，所以重要答案仍要看引用。
- 複雜合併儲存格、圖片型 Excel、掃描 PDF 可能需要額外讀取器。
- Wiki 是整理內容，不保證永遠正確或最新。
- 修正只對能描述和比對的相似情境有效，不能保證所有新問題都自動套用。
- 大量資料的第一次讀取和建立 index 需要時間。
- OneDrive 跨電腦同時寫入仍有同步衝突風險。
- 使用雲端 AI 時，送入模型的證據片段需遵守資料政策。

最安全的使用習慣是：

```text
保留唯一原檔
→ 只放副本進 inbox
→ 重要回答查看原始引用
→ 發現錯誤立即說「這個回答錯了」
→ 確認成熟答案後才說「保存這次回答」
→ 定期執行 status 和 lint
```
